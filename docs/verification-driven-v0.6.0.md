# Verification-driven agent architecture (v0.6.0)

## Mandatory integration contract (multi-agent mode)

This layer supplements, never replaces, the v0.5.1/v0.5.2 independent admission and acceptance gates. It is an offline checker invoked by the host before each proposed native BUILD/MUTATE/SOLVE/REPAIR and before declaring reproduction acceptance. In single-agent fallback use the separate existing baseline and mark fallback; do not claim this multi-agent admission. Read-only work gains no mutation permission. The executor remains the only native writer. The host must enforce actual permissions, verify current session and job identity, perform fresh live readback, and stop if any required checker is unavailable or returns a non-candidate. No new connector or live authorization is implemented by this script. Never use offline PASS as evidence of successful simulation. 

1. Freeze task criteria, deadline, revisions, resource identity, active roles and expected observations. Load `benchmarks/agent-feature-map.json` and run `python scripts/verification_gate.py feature-map`; this checks actual repository paths only. Select features relevant to the task. For each record actual discovered provider/API, input revision, native result and evidence location. Do not invent tool names or mark a feature complete based on prose.
2. Reconcile original jobs and operations; unknown state or expired budget blocks new submissions. For repair use `scripts/recovery_memory.py` and preserve the NEW/HOLD result; recheck live reservation and job immediately before authorized execution. A historical record or knowledge card is not authority.
3. For each scoped action, capture original artifact bytes in a private task workspace: provider identity/readback, writer lease/isolation, checkpoint, budget, independent supervisor and physics review when required. For repair capture matching reservation. Bind receipt and artifact hashes to immutable task/case/revision/spec/snapshot/stage/action. Hashes establish local byte integrity, not truth or origin authentication. Capture receipts independently, with real worker identities and UTC validity windows determined by task; refresh after model, action, criteria, job or review changes. Never write fabricated PASS receipts.
4. Use `python scripts/verification_gate.py verify request.json /path/to/workspace`. Request contains mode `admit` or `acceptance`, the existing v051 snapshot (see `scripts/check_multi_agent_v051.py` and its tests), and receipt references `[{"path":"receipt.json","sha256":"<64 lowercase hex>"}]`. Snapshot revision, spec_hash and snapshot_hash must be real SHA-256 digests. Receipt structure: see `schemas/verification-receipt.schema.json`. Actual receipt source and observation must locate native readback or independent review; each artifact path is relative to workspace, hash exact. Independent supervisor/physics/acceptance worker must match the current review records. `EVIDENCE_BOUND_CANDIDATE` means only the declared offline conditions and local bytes match. Any other action, missing file, invalid scope or hash, stale evidence or HOLD stops this proposed action. Preserve result; only execute if live host enforcement and current native state also pass. No checker may grant new permissions, infer current job state from a disconnected channel, or interrupt an unrelated job.
5. After execution, read back actual effects. Invalidate dependent receipts and results after edits; preserve previous checkpoints. Record native terminal status separately from scientific verification. For reproduction, evidence categories correspond to G1 source inputs; G2 geometry and effective physics; G3 mesh and native solution; G4 postprocessing and independent acceptance; G5 scoped persistence/editability/reopen. Keep exact task-specific QoI thresholds, conservation definitions, grid/time checks, and acceptance criteria from existing contract; this checker does not replace calculations or change thresholds. G5 includes actual required native replay/editability evidence, not just file existence. Missing mandatory evidence is HOLD/NOT_RUN. No automatic claim of scientific success.
6. Recorder stores real outcomes in private recovery DB; Orchestrator proposes new deterministic checks for repeat failures. Add a minimal failing regression first, a bounded fix, a positive/negative test and an applicability statement; require independent review before changing any canonical rule or guard. Never auto-promote a knowledge entry from a single successful run, rewrite acceptance thresholds, or learn from held-out cases. No automated self-modification or Git push by agent.

## Formal and software verification

- `python scripts/verification_state.py`: finite explicit Python state exploration (two writer candidates, up to two revisions/submissions and two abstract time ticks), checks transitions, stale reviews, veto, unknown job, deadline and acceptance invariants. This is an abstract model; no proof of real host/provider concurrency, liveness, hard cutoff or CFD correctness.
- `docs/formal/Coordination.tla` and `.cfg`: matching abstract TLA+ specification, finite bounds. Run official TLC 1.7.4 in separate temporary state directory: `java -cp /path/to/tla2tools.jar tlc2.TLC -config Coordination.cfg Coordination.tla` from `docs/formal`; use `-metadir` outside source tree for production. The CI installs pinned release (upstream published checksum), checks invariants and temporal safety properties. No liveness or real solver refinement proof. The Python explorer is independently executed, not a claim TLC ran.
- `python -m pytest -q tests/test_verification_gate.py tests/test_verification_properties.py`: positive/negative controls and Hypothesis generated state sequences. Install `hypothesis` for the latter; missing dependency explicitly skips locally, but CI requires it. Existing v051 policy tests remain mandatory.
- `python scripts/verification_mutations.py`: isolated copy, eight named targeted mutations in actual gate/model functions. Each must fail the unchanged tests; errors are not kills. Optional full `mutmut` campaign on Linux/WSL can inspect a dedicated disposable worktree with path-to-mutate restricted to the new guard; record equivalent mutants and never count import/collection errors as kills. No full campaign claimed.
- `python scripts/verification_release_gate.py --output /outside/repo/Paper2Simu-v0.6.0.zip`: offline regression, feature-map, abstract model, targeted mutation and release manifest/knowledge hash checks. `--require-hypothesis` fails if unavailable. `--tlc-jar` runs TLC when installed; `--require-tlc` blocks if missing. No native or benchmark claim; release report must distinguish NOT_RUN. The GitHub Actions workflow requires both optional tools for its own check, runs existing full regression, and can be configured as a required branch status check by the repository administrator. CI configuration does not enable branch protection by itself. Do not publish a native-validated release from offline passes alone.

## Agent evaluation and experimental controls

Use the existing 0.4.5 single-agent and 0.5.0 multi-agent controls, 0.5.2 supervised baseline, and 0.6.0 with knowledge retrieval/verification toggled only in evaluation mocks or isolated authorized tests. Freeze cases, expected outcomes, budgets, model/host/tool versions, seed, evaluator and criteria before running. Never disable live mandatory permissions to create a control group. Use `scripts/verification_eval.py` on independently scored case records: exact same case IDs and configuration IDs, missing cases fail, disallowed-action attempts and false acceptance counted separately; evaluate repeated runs for reliability. Include native/scientific results and time/cost only if actually observed. Keep development and holdout separate; report limitations and sample sizes. Compare ablations (knowledge-only, plus checks, plus independent reviews) on the same task distribution with equal budgets or report differences. No benchmark scores from other projects presented as Paper2Simu results.

## Upstream sources and integration scope

- SQLite transactions: https://www.sqlite.org/lang_transaction.html (actual local persistent reservation store). JSON Schema: https://json-schema.org/ (receipt protocol). Existing v051 policy helpers reused rather than new parallel authorization logic.
- Anthropic harness research: https://www.anthropic.com/research/effective-harnesses-for-long-running-agents and https://www.anthropic.com/research/harness-design-long-running-apps — durable feature lists, incremental progress, independent verification. OpenAI SDK testing and tracing: https://openai.github.io/openai-agents-python/testing/ and https://openai.github.io/openai-agents-python/tracing/ — mock deterministic execution, tool-call evidence; no SDK or external trace export required.
- TLA+/TLC: https://github.com/tlaplus/tlaplus/releases/tag/v1.7.4 and https://docs.tlapl.us/using:tlc:start — abstract model checking. Hypothesis: https://hypothesis.readthedocs.io/en/latest/stateful.html — genuine stateful property tests. mutmut: https://mutmut.readthedocs.io/en/latest/ — full mutation framework remains optional, targeted independent runner provided.
- tau2-bench: https://github.com/sierra-research/tau2-bench — task-state/outcome evaluation design, not a CFD dataset or a benchmark run here. GitHub status checks: https://docs.github.com/en/pull-requests/reference/status-checks — configured workflow; required status checks need separate repo settings.
- All local new code and tests are original; no upstream source copied, no public/private telemetry upload by default. Vendor software and knowledge sources remain subject to their respective licenses.
