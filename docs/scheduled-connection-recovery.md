# Scheduled solver connection recovery

For v0.6.3 first apply the [host connection supervisor](connection-supervisor-v0.6.3.md) on every scheduled turn. Missing tool catalog with healthy transport follows the bounded host refresh path when an authorized adapter exists. The following attachment and reconciliation checks remain mandatory; a refresh is never a solver restart or proof of recovery.

## Set up the scheduled task

Record the host, solver family, registered MCP server ID, expected native solver endpoint or approved session reference, output directory, task ownership, and cutoff as a date and time with a timezone or UTC offset. For a recurring window, record its recurrence and timezone. Keep the current job IDs, run/model identities and checkpoint paths in the task's existing durable journal so the next turn can recover them without chat history. Keep connection credentials in the configured provider. A COMSOL MCP transport URL and the COMSOL Multiphysics backend host/port are separate fields.

Use the following text in the saved task prompt, along with the task's existing inputs, cadence, cutoff, budgets and authorization.

> Load the Paper2Simu skill and follow its scheduled connection recovery instructions on every turn. Use the solver MCP provider configured for this task in the current scheduled turn. Check the connector, attached solver, original jobs and submission cutoff before taking action. Retain known job IDs in the task journal. After the cutoff, finish monitoring existing jobs and follow the configured idle behavior. Preserve the schedule and report any blocked check or recovery.

## Check each turn

Read the task's `resume.md` first if present. Use the underlying [research plan and trial journal](research-plan-and-handoff.md) for phase, prior submission identities and next action. Refresh the summary after an observed state change. Verify the original job through the provider or native records below.

1. **Verify access from this scheduled turn.** Discover the configured provider and make its read-only status call. Report tool discovery, successful MCP response and backend attachment separately. If the registered loopback HTTP endpoint returns `502` before an MCP tool response, run the [loopback HTTP 502 check](#loopback-http-502) before trying to attach to the solver. For other tool, transport or access failures, retain the exact error (redacted) and the last verified state. Files, job manifests and native logs already available to this turn may still be read, with timestamps and their source recorded. Keep unverified state unknown. Wait for the next scheduled check for transient failures. For a policy denial, report the blocked operation and stop retrying that operation until its access changes. Use registered MCP calls for solver control. A terminal from an earlier turn, `write_stdin` and GUI automation are outside this route.
2. **COMSOL.** Read `comsol_queue_status` first for `runtime_id`, `output_root`, `active_jobs`, `recovery_pending` and `submission_budget`. Check known IDs using `comsol_job_status`. When the JVM is idle, read `comsol_status` for `connected` and the native endpoint. If `comsol_status` reports `JVM_BUSY`, keep polling job metadata and defer the native read. An MCP response verifies tool access. An empty `active_jobs` list applies to that runtime only.
3. **Fluent.** Discover the configured official PyFluent MCP schema. Use `session_status` or the installed provider's documented read-only equivalent when present. Use the original job's run/case identity, durable runner status and native transcript for progress and termination. If the official MCP is absent, continue with available read-only evidence and report live control as unavailable. If the Windows launch log shows a compute-node startup hang after license checkout, use the [MPI startup preflight](fluent-windows-mpi-preflight.md) to interpret the launch evidence. Keep an unresolved job in place and handle any separately authorized diagnostic launch outside scheduled attachment recovery. A gRPC or native report error belongs to that operation. Record any independent evidence of session availability separately.
4. **Recover an attachment only when authorized and identified.** If the registered MCP responds but the native backend is unconnected, verify the saved target against the current existing process or trusted session record. With COMSOL, use `comsol_connect` on the verified Multiphysics endpoint. With Fluent, use the installed provider's explicit attach-to-existing mode and its required verified session arguments. If attach mode, target identity or ownership is uncertain, report the blocker. Keep a single recovery attempt per turn. Leave any active or ambiguous prior job in place. Preserve original processes, models and artifacts, and avoid starting another solver, changing permissions, or falling back to a legacy control path.
5. **Reconcile before continuing.** After an attach, check the returned native identity and the original job IDs. After a lost receipt, query by the original `operation_id` if the configured COMSOL tool exposes it. On runtime change or missing, historical or `recovery_pending` status, reconcile against the exact run's native log, job records and checkpoint artifacts. Preserve an unresolved job or submission acknowledgement as unknown. Keep monitoring and independent authorized work available while blocking duplicate submissions. A live connection or a readable checkpoint does not establish that a particular solve completed. For COMSOL `ModelUtil.loadRecovery`, resolve recovery folders on the MCP client's filesystem, preserve the originals, and verify the reopened solution with a fresh tag and the target dataset. See [COMSOL ModelUtil](https://doc.comsol.com/6.4/doc/com.comsol.help.comsol/comsol_api_general.47.15.html).
6. **Apply cutoff and budget separately.** Compare against the dated cutoff in the configured zone on each turn, including after midnight. A cutoff or a submission cap closes only new submissions. Continue checking authorized in-flight jobs and perform authorized finalization when safe. Once all tracked jobs are known to be idle or terminal, follow the task's explicit continuation or pause setting. If pause is requested but unsupported, report that and leave the task entry intact. Preserve the schedule through errors, exhausted quotas and cutoff. Task deletion requires separate explicit user direction.

Record time with timezone, host and task ID, provider and tool result, backend identity or unknown state, runtime/job IDs, last verified activity, submission decision and next action. Use the existing audit location and redact credentials. Keep native failures and report extraction status distinct from the connection status.

## Loopback HTTP 502

Use this check only when the registered HTTP MCP URL points to `127.0.0.1`, `localhost`, or `[::1]` on the machine running the MCP client and connector. Use the configured hostname, port and path. The COMSOL Multiphysics backend port is a separate endpoint.

1. **Compare proxy and direct evidence.** Match the Codex failure timestamp and destination to the proxy log. From the same workstation and execution context when available, probe the same URL directly with a short timeout. For a Windows operator, replace `<registered-loopback-MCP-URL>` with the configured loopback URL, with any credentials omitted:

   ```powershell
   curl.exe --disable --noproxy '*' --connect-timeout 3 --max-time 5 --silent --show-error --output NUL --write-out '%{http_code}\n' '<registered-loopback-MCP-URL>'
   ```

   This GET checks HTTP reachability without carrying an MCP token or calling a solver tool. A response attributable to the expected connector, including a `401` without credentials or a protocol-appropriate `405`, can show that the local listener was reached. It takes successful MCP tool discovery and a read-only call to verify the client connection. `--noproxy` controls curl's proxy use. If a VPN or TUN still intercepts the request, verify the actual route before treating the result as direct.
2. **Correct the matching loopback exception.** When the proxy log shows the failing request being forwarded (for example by Clash `GLOBAL`) and the same URL responds as expected on the direct route, use an authorized, exact bypass for the hostname or address in the registered URL in the proxy settings effective for that client. Keep the rest of the proxy configuration and the connector's authentication in place. If the direct route also fails or the proxy evidence is missing, record the observations and leave the proxy cause unconfirmed. Keep the original job status unknown until it can be checked.
3. **Renew the client connection and reconcile.** After the exception takes effect, use the client's supported reconnect or refresh action. If the current client retains an initialization failure and has no working refresh, save the handoff and have the operator re-open or restart only the affected Codex client while the existing MCP connector and solver stay running. Verify access in the actual scheduled turn with the registered provider. For COMSOL, read `comsol_queue_status` and `comsol_job_status` for the original IDs, then follow the reconciliation and cutoff steps above. While the route or original job remains unverified, preserve the schedule and withhold replacement submissions. Carry the redacted proxy route, direct result and client recovery outcome into the existing audit record.

## Roll out and verify on each host

1. Update the installed skill content and make the saved task explicitly load Paper2Simu. If an existing task embeds the old terminal instructions, replace those instructions while preserving its cadence, task scope, solver owner, cutoff and budgets. For a missing task, recreate it only when the user has authorized it and its original scope is known.
2. Use the real scheduled execution identity and project context for a read-only check. On hosts with a loopback HTTP provider, confirm that the exact registered host bypasses the proxy in the scheduled client's effective configuration. On the two COMSOL hosts, verify registered MCP access, the expected backend, and an existing job ID or checkpoint record. On the two Fluent hosts, first verify each host's actual registered provider and supported status tool. Report missing tools as unverified and confirm the task can still read its own progress evidence. A manual chat check alone does not validate scheduled access.
3. Verify a closed submission window still allows status checks, an active job can still be monitored, and the schedule entry survives after cutoff. Validate the first real cutoff/cross-midnight handoff per host. Keep live rollout pending until these observations are recorded.

A skill-content update can be applied with the existing compatible MCP runtime. When upgrading the connector runtime too, use the [connector migration instructions](connectors.md#submission-window-and-recovery) and its version-matched launcher configuration.

## v0.6.1 scheduled checks

Apply [runtime reliability](runtime-reliability-v0.6.1.md) to the actual scheduled execution context, not a separate successful CLI session. The direct loopback probe is deliberately credential-free and does not perform MCP initialization. Do not reset the case clock at reconnect. Runtime rejects new queued jobs while historical recovery records or unreadable journals remain unresolved.
